# 机房链路切换演练沙盘（Link Handover Drill）

机房维护前，值班员需要把一条备份流从旧链路迁到另一条链路。本项目是一个
**Flask 本地演练页**：内置两条连续编号（1..N）的样例报文流，可在网页上调整
两条链路的延时与切换时限，选择一条流执行迁移，并以动画时间线回放全过程，
最终展示**交付顺序、每个报文所走链路、切换结果与正确性自检**。

## 一、模拟的协议语义（make-before-break）

| 规则 | 实现 |
| --- | --- |
| 先连后断 | 切换开始（虚拟时间 400ms）后，迁移流的**后续报文先经新链路试发**，旧链不立即断开 |
| 旧链排空才放行 | 接收端重排序缓存中，新链报文一律按住不放；旧链在途报文全部按编号交付后才放行新链缓存 |
| 新链窗口 = 4 | 发往新链但**尚未交付给应用**的报文最多 4 个；窗口满时只暂停这一条流，另一条流不受影响 |
| 超时回退 | 旧链在切换时限内未排空 → 退回旧链：未交付的试发报文经旧链**补发**，新链上迟到的副本（含在途与缓存）一律**丢弃** |
| 有序且仅一次 | 无论成功还是回退，接收端都按编号 1..N 交给应用，每包恰好一次（重排序缓存 + 去重） |

时间模型：离散 tick（1 tick = 50ms），同一条流每 200ms 生成一个新报文；
链路延时按 tick 取整。同 tick 内顺序固定为「到达 → 交付（释放窗口）→ 判定 → 发送」，
因此每次运行结果完全确定、可复现。

## 三、用 Docker Compose 启动（推荐）

```bash
cd link-handover-drill
docker compose up --build
```

浏览器打开 <http://localhost:8000> 。容器内含健康检查
（`GET /api/health`），镜像基于 `python:3.12-slim`，gunicorn 单进程 4 线程。

停止：`docker compose down`

## 四、不用 Docker 的本地启动（调试用）

```bash
pip install -r requirements.txt
python -m app.app          # 监听 0.0.0.0:8000
# 测试
python -m pytest tests/ -v
```

## 五、网页操作说明

1. **参数设置**：L1/L2 单向延时与切换时限均可设到 **60000ms（60 秒）**
   （延时 50–60000ms、时限 100–60000ms，仍按 50ms 刻度输入）、
   迁移流 1（L1→L2）或流 2（L2→L1）、每条流报文数（1–50，默认 14）。
2. 五个**预置场景**一键填入：
   - 场景 A：正常切换成功（新链稍快、时限宽松）；
   - 场景 B：旧链拥塞超时 → 回退补发、丢弃新链迟到副本；
   - 场景 C：新链高延时，4 包窗口反复打满、仅暂停迁移流；
   - **场景 D：备份新链 60s 长延时，窗口 `[3,4,5,6]` 从 tick 24 卡到
     tick 1207（约 59.2s），交付释放当刻续发，随后成功**；
   - **场景 E：旧链 30s 拥塞、时限 8s，长时延下超时回退、当刻旧链补发**。
3. 回放内容：
   - **切换总览**：迁移方向、成功/回退徽标、虚拟时钟、新链窗口占用 `n/4`、
     时限倒计时、最长受阻时段；
   - **③ 紧凑时间线（长时延主视图）**：按真实虚拟时间比例绘制——
     红色斜纹带即**窗口满连续受阻时段**（带内显示窗口内编号、持续时长、
     首末 tick），紫色/绿/红竖线为切换开始/成功/回退，蓝/绿细刻度为
     发送/交付时刻，底部紫色阶梯条为**窗口占用 `n/4`**（打满变红），
     白色游标尺与回放同步；上方统计条显示**引擎实际处理的刻度数 /
     时间线槽位 / 跳过的空刻度数 / 压缩受阻段数**；
   - 受阻段汇总按钮可**点击跳转到该时段起点**继续播放；
   - **报文泳道**：每个报文在 L1/L2 上的移动、等待（紫色）、交付（绿色）、丢弃（红色）；
   - **交付顺序**：应用实际收到的编号序列，每个色块标注链路与「原发/新链试发/旧链补发」；
   - **事件时间线**：发送、到达、交付、丢弃、暂停、切换开始/成功/超时等事件；
     压缩模式下每个受阻段只输出一条首末汇总（末刻度事件不重复刷屏）；
   - **正确性自检**：5 项断言（两条流各按编号交付且每包一次、排空顺序、回退补发、窗口上限）。
4. 支持 1×/4×/10×/60×/瞬时 播放与重新播放。长时延场景建议直接用 60× 或瞬时，
   再用紧凑时间线与受阻段跳转定位。

## 六、主要 API

- `GET /` 演练页面
- `GET /api/health` 健康检查
- `POST /api/simulate` 入参 JSON：
  `delay_l1_ms`、`delay_l2_ms`（50–60000）、`deadline_ms`（100–60000）、
  `moving_stream`(1|2)、可选 `packets_per_stream`（1–50）、可选 `compact`(bool)；
  返回完整事件时间线、交付序列、丢弃记录、切换结果与自检。
  参数越界或类型错误返回 HTTP 400 与中文错误信息。

**长时延压缩与向后兼容**：

- 引擎始终跳空刻度运行：只处理「切换开始/时限到点/报文到达/发送时机」刻度，
  cooldown 按跳过的 gap 批量推进；窗口满后不再逐 tick 试发，直接跳到下一次
  窗口可能变化的刻度（交付/丢弃/超时）。50ms 刻度、200ms 发包节奏、同 tick
  「到达 → 交付（释放窗口）→ 判定 → 发送」顺序完全不变。
- 连续且窗口内编号集合相同的 `send_blocked` 被压缩为一个受阻时段
  `blocked_spans[]`：含 `stream/window/first_tick/last_tick/first_ts/last_ts/
  blocked_ticks/duration_ms`（另附 `start_*`、`end_*`、`first_blocked_tick` 等别名）。
- `stats`：`processed_ticks`（引擎实际处理刻度数）、`total_ticks`（0..last 的
  槽位数）、`skipped_ticks`、`mode`、`blocked_span_count` 等；顶层另有
  `processed_ticks` 别名。`window_occupancy[]` 给出迁移流窗口占用变化点。
- **当 `delay_l1_ms/delay_l2_ms ≤ 3000 且 deadline_ms ≤ 5000`（旧参数范围）
  且未显式传 `compact` 时，响应 `events` 与旧版逐字一致**：每个受阻 tick 一条
  原样的 `send_blocked`（键顺序也一致）。超出旧范围自动 `mode=compact`：
  每个受阻段在 `events` 中只保留首、末两条带 `edge:"first"|"last"` 的事件
  （首条带完整首末信息）。任何范围都可显式传 `"compact": true|false` 覆盖。
- 典型量级：60s 新链延时 + 14 包（场景 D）只处理 37/3621 个刻度、94 条事件；
  双 60s + 50 包的极端组合处理 154/14421 个刻度、约 330 条事件，耗时个位数毫秒。

## 七、已完成的验证（交付前核对）

- 单元/集成测试 **40 项全部通过**（`pytest tests/ -q`）：原 22 项覆盖成功路径、
  超时回退、迟到新链副本丢弃、窗口打满仅暂停迁移流、非迁移流不串链、流 2
  迁移对称性、API 校验与页面渲染；新增 18 项覆盖 60s 上限、受阻段首末刻度、
  跳刻度统计、**交付释放当刻续发（tick 1208 交付 seq3 → 同 tick 发 seq7）**、
  **超时回退当刻补发（场景 E tick168、场景 B tick20 超时与 old-resend 同 tick）**、
  长受阻期间另一条流按 4-tick 节奏照发照收、旧范围逐条事件兼容、随机长参数不变量。
- **4653 组差分测试零分歧**：把新引擎 `compact=false` 展开出的 `events`
  （dict 与保留键顺序的 JSON 文本）、`delivery/discards/handover/max_ts`
  与 git HEAD 原版逐 tick 引擎逐一比较，参数覆盖延时 50ms–60s、时限
  100ms–60s、N=1–50、两种迁移流（含 4000 组随机）；压缩出的 `blocked_spans`
  也与“从原版事件重新压缩的首末段”完全一致。期间发现并修复了一个真实边界
  缺陷：最后 4 包恰好占满窗口（`next_seq>N`）时，调度器一度漏掉尾段首个受阻刻度。
- **前端 jsdom 冒烟**：用真实 API 夹具（场景 C/D/E）在 jsdom 中实际执行
  `app.js` 的 `setupScene/seek/jumpTo`，紧凑时间线红带数、受阻汇总 chips、
  引擎刻度统计、播放到结尾游标尺 100%、2N 个交付 chips、自检全绿、点击受阻段
  跳转并高亮等断言全部通过；`node --check app.js` 语法通过。
- **真实 HTTP 自测**：按 Dockerfile 的等价方式用 gunicorn
  （`app.app:app`, 1 worker/4 threads）启动，`/api/health`、`/`、
  `/static/app.js`、`/static/style.css` 均 200；五个预置场景 A–E 的 API
  输出与设计一致（D：37/3621 刻度、3 个受阻段；E：41/813、回退），
  60000ms 入参 200、60001ms 入参 400。

  无 Docker 未能执行。
- 历史验证（原参数范围）：**500 组随机参数扫描**全部满足两条流交付严格
  1..N、每包一次、窗口峰值 ≤4；开发过程中修复的两处真实缺陷（成功后漏检
  窗口、超时判定晚一个 tick）在新引擎中保持修复并被差分测试锁定。

## 八、未完成 / 局限项

- **本机未安装 Docker / Docker Compose**，`docker compose up --build`
  未在当前环境实跑；已通过 YAML 解析、Dockerfile 未改动且人工核对、以及
  同命令的 gunicorn 本地实跑验证。请在有 Docker 的机器上执行一次
  `docker compose up --build` 做最终确认。
- **没有可用的图形浏览器**（无 Chromium/Chrome/Playwright），未做像素级
  视觉与真实点击验证；前端逻辑已用 jsdom 真实执行 DOM/回放/跳转代码路径，
  但布局观感、动画帧率与窄屏横向滚动仍建议人工打开页面确认一次。
- 页面动画为**确定性回放**（后端一次算完时间线，前端按虚拟时间播放），
  不是实时网络收发；适合演练逻辑推演，不用于性能压测。
- 未做用户鉴权与持久化：每次请求独立计算、无服务端共享状态，定位为本地工具。
- 仅模拟单向延时与固定发包间隔，未建模丢包、乱序、带宽拥塞等更复杂链路行为。
- 为兼容不同调用习惯，`/api/simulate` 新结果里带了少量同义别名字段
  （如 `blocked_periods`、`processed_ticks` 顶层别名）；旧字段与旧事件
  结构均未删除或改义。
